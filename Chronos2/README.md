# Chronos-2 zero-shot study (Benchmark II) — univariate vs cross-learning

A zero-shot evaluation of **`amazon/chronos-2`** on the Chronos paper's
**Benchmark II**, using the *same* harness as the Chronos-T5 reproduction in
[`../Chronos_benchmark`](../Chronos_benchmark). This project is **Chronos-2 only**:

1. **Univariate vs cross-learning** — does Chronos-2's in-context learning (full
   cross-learning mode, the report's Benchmark II setting) beat plain univariate
   inference on the 25 datasets?
2. **Reproduction check** — do our numbers match the **Chronos-2 paper's** reported
   Benchmark II result (arXiv:2510.15821, Table 5)?

> The head-to-head **vs Chronos-T5** (dashboard, per-dataset scatter, forecast plots,
> efficiency) lives in the sibling comparison project
> [`../chronos2_t5/zero-shot/`](../chronos2_t5). The three projects are parallel:
> `Chronos2` (this, C2), `Chronos_benchmark` (T5), `chronos2_t5` (their comparison).

The harness is **identical** to the Chronos-T5 benchmark — same dataset registry,
same `MAX_SERIES=1000` cap, same gluonts `split`, same MASE +
`MeanWeightedSumQuantileLoss` (seasonality inferred per-frequency), same
aggregated relative score (`gmean(model / Seasonal-Naive)`).

## What's different about Chronos-2 (vs token-based models like Chronos-T5)

Full write-up: [`docs/CHRONOS2_VS_T5.md`](docs/CHRONOS2_VS_T5.md). In one table:

| axis | Chronos-T5 | Chronos-2 |
| --- | --- | --- |
| tokenization | scale → **quantize to a token vocab** → sample | **patch** raw values → residual MLP, **no vocab** |
| scaling | per-series **mean scaling** | **InstanceNorm** (standardize) + optional `arcsinh` |
| output | 20 **sampled** paths → empirical quantiles | **direct quantile head** (deterministic) |
| multivariate | unsupported | native, via **group attention** over a group of series |
| gluonts object | `SampleForecast` | `QuantileForecast` |

Because Chronos-2 emits quantiles directly there is **no sampling and no seed** —
inference is reproducible by construction. We request the same 9 quantile levels
(0.1…0.9) T5 used so WQL is computed on an identical grid.

## The two modes — exactly as the Chronos-2 report does on Benchmark II (§5.1)

Benchmark II is a **univariate** benchmark (each task is a standalone 1-D series,
no declared variates, no labelled covariates). The report therefore does **not**
run shared-dynamics multivariate here — that is reserved for fev-bench / GIFT-Eval.
The two settings it reports, which we mirror:

* **univariate** — every series forecast independently (each is its own group, so
  group attention is inert); the apples-to-apples counterpart of Chronos-T5.
* **cross_learning** — Chronos-2's **full cross-learning** mode: inputs stay 1-D,
  but every item in a batch is assigned the *same* group id so group attention
  shares information across all series in the batch (`cross_learning=True`,
  group/batch size `CROSS_LEARNING_BATCH=100`, as in the report). The group **is**
  the batch, so results are batch-size dependent — intended, and matching the
  report. Cross-learning helps most when series have short histories (common in
  Benchmark II), e.g. on `monash_m1_yearly` it improves MASE 3.83 → 3.55.

> Genuine shared-dynamics multivariate (stacking aligned variates into a
> `(n_variates, length)` item) is how the report evaluates fev-bench / GIFT-Eval,
> not Benchmark II, so it is intentionally not used here.

## One-shot (LoRA fine-tuning)

The Chronos-2 counterpart of the Chronos-T5 one-shot in
[`../Chronos_benchmark`](../Chronos_benchmark) (`finetune_oneshot.py` +
`run_oneshot_official.py`). It keeps the **same paper-faithful one-shot recipe** so the
two are directly comparable — per dataset, train `prediction_length` = the eval horizon,
the last `horizon` points held out (no leakage), **lr 1e-3 annealed linearly to 0 over
1000 steps**, AdamW, grad-clip 1.0, seed 0 — and, exactly like the T5 script, writes the
optimization as an **explicit PyTorch loop** rather than calling the library
(`Chronos2Pipeline.fit` / HF `Trainer`).

Two things differ by **architecture, not recipe**:
* Chronos-2 has **no token vocabulary / ChronosTokenizer**. Its `forward()` takes the raw
  `context` + `future_target` and returns the **quantile loss** directly (patching,
  InstanceNorm and the objective are all internal), so there is no
  tokenize→seq2seq-cross-entropy step — we feed raw windows and read `out.loss`.
* We adapt with **LoRA** (peft) rather than full fine-tuning so a 120M-param model
  fine-tunes on a local GPU without memory exhaustion (only ~1% of params carry
  gradients). Rank/alpha/target modules mirror Chronos-2's official LoRA defaults
  (attention `q/k/v/o` + the output patch-embedding layer).

One-shot is evaluated in **univariate** mode — the apples-to-apples counterpart of the
T5 one-shot and of C2 zero-shot univariate. (The C2-vs-T5 one-shot head-to-head itself
will live in [`../chronos2_t5/one-shot/`](../chronos2_t5).)

## Setup on a new machine

Datasets download automatically on first run (into the HuggingFace cache); you only
need a Python environment.

**1. Create the environment** (Python 3.11) — either is fine:

```powershell
# Option A: dedicated conda env
conda env create -f environment.yml
conda activate chronos2

# Option B: reuse the sibling benchmark's env (identical deps)
conda activate chronos_bench

# Option C: venv + pip
python -m venv .venv ; .\.venv\Scripts\Activate.ps1 ; pip install -r requirements.txt
```

**2. Install PyTorch for your GPU** (kept out of the env/requirements files so the
CUDA build is correct):

```powershell
# GPU, CUDA 12.8 (what this was measured on):
pip install torch==2.9.1 --index-url https://download.pytorch.org/whl/cu128
# CPU-only: pip install torch==2.9.1
```

## Run

```powershell
conda activate chronos2          # or chronos_bench
python src/config.py             # confirm paths resolve on this machine

# quick wiring check (downloads amazon/chronos-2 on first use, ~1 min)
python src/smoke_test.py

# full study: 25 datasets x {univariate, cross_learning}
python src/zero_shot/run_zeroshot_chronos2.py

# one-shot: LoRA fine-tune per dataset (-> models/ft_oneshot/), then evaluate
python src/one_shot/finetune_oneshot_chronos2.py   # writes per-dataset adapters + manifest.csv
python src/one_shot/run_oneshot_chronos2.py        # -> oneshot_chronos2_results.csv + CHRONOS2_ONESHOT_REPORT.md

# build the deliverable notebook (--execute embeds results + charts inline)
python src/make_notebook.py --execute
```

Outputs:
- `results/zeroshot_chronos2_results.csv` — per `(dataset, mode)`: MASE, WQL,
  grouping stats, latency, peak GPU memory.
- `results/CHRONOS2_REPORT.md` — aggregated relative score (C2 univariate vs
  C2 cross-learning vs **the Chronos-2 paper**), per-dataset table, grouping table,
  inference efficiency.
- `results/forecasts/chronos2/` — one forecast plot per dataset (+ overview grid).

(The Chronos-T5 head-to-head artifacts live in `../chronos2_t5/zero-shot/`.)

> Datasets are read from the local HuggingFace cache (already populated by the T5
> benchmark). The Chronos-2 weights download once from the Hub; after that you can
> set `HF_HUB_OFFLINE=1` and `HF_DATASETS_OFFLINE=1` to run fully offline.

## Portability / configuration

All paths resolve at runtime from the project root via `src/config.py`, so the study
is portable: clone it anywhere and the scripts find their own results / reference
dirs with no edits. Each path can be overridden by an environment variable:

| variable | overrides | default |
| --- | --- | --- |
| `CHRONOS2_ROOT` | project root | parent of `src/` |
| `CHRONOS2_RESULTS` | result CSV / MD dir | `<root>/results` |
| `CHRONOS2_REFERENCE` | reference CSV dir | `<root>/reference` |

Run `python src/config.py` to print the resolved layout before launching a long run.
